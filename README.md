## Quickstart

```bash
# 1. clone
git clone git@github.com:Touutae-labs/friendly-system.git && cd friendly-system

# 2. install everything (Go 1.22+ assumed; installs atlas + wgo + wire + mockery)
make install

# 3. run tests — works with zero state, no DB needed
make ci

# 4. seed DB + start server (writes ./data.db, server on :8080)
make seed
make dev

# 5. in another shell — try a few orders
curl -s http://localhost:8080/health
curl -s http://localhost:8080/orders/validate \
  -H 'Content-Type: application/json' \
  -d '{"customer_id":"C001","order_type":"buy","quantity":"0.5","quoted_price":"42210"}'

# or open api/orders.rest in VS Code (REST Client extension) and Send Request
```

> **Linux/macOS:** `make install` installs everything from official channels.
> **Windows users** without `make`: see the [Without make](#without-make) section.

**Architecture intent.** Vertical-slice ports & adapters. Each
`domain/module/<name>/` is a self-contained business concern (`core.go` =
rule logic, `repository.go` / `provider.go` = port interface, `memory.go` =
the in-memory adapter that ships with the module). Production-shaped
adapters live in `domain/repositories/` and use **GORM** against any
SQL backend (SQLite, Postgres, MySQL). `domain/service/validator/`
orchestrates the four modules. **Google Wire** (`wire/`) is the
composition root, with `wire_gen.go` carrying the compile-time-checked
DI graph (two injectors: one for the in-memory mode, one that takes
`*gorm.DB`). Full rationale is in
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Production evolution
path is in Part 4 §4.

## Requirements

- **Go 1.22+**
- **Module dependencies** (fetched on first `go mod tidy`):
  - [`shopspring/decimal`](https://github.com/shopspring/decimal) — exact decimal arithmetic for money
  - [`google/wire`](https://github.com/google/wire) — compile-time DI (codegen)
  - [`gorm.io/gorm`](https://gorm.io) + [`glebarez/sqlite`](https://github.com/glebarez/sqlite) — ORM + pure-Go SQLite driver (no CGO required)
  - [`stretchr/testify`](https://github.com/stretchr/testify) — Mockery runtime
- **Dev tools** (only required if you run the corresponding make target; generated outputs are committed so `make ci` works without any of them):
  - `make seed` → [Atlas](https://atlasgo.io). Windows binary: `curl -L https://release.ariga.io/atlas/atlas-windows-amd64-latest.exe -o $(go env GOPATH)/bin/atlas.exe`
  - `make dev` → `wgo`. Install with `go install github.com/bokwoon95/wgo@latest`
  - `make wire` → `wire`. Install with `go install github.com/google/wire/cmd/wire@latest`
  - `make mock` → `mockery`. Install with `go install github.com/vektra/mockery/v2@latest`
  - On Windows / Git Bash: make sure `$(go env GOPATH)/bin` is in your `PATH`.
- A REST client for `api/orders.rest`. Easiest is **VS Code + REST Client extension** (`humao.rest-client`). `curl` works too — examples below.

## Make targets

| Target | Does |
|---|---|
| `make install` | install all dev tools: `wire`, `mockery`, `wgo`, `atlas`, plus `go mod download` |
| `make ci` | `go vet ./...` + `go test -race ./...` |
| `make seed` | `atlas schema apply --to file://schema.sql` against `./data.db`, then insert sample accounts + one daily total via `cmd/seed` |
| `make dev` | `wgo run ./cmd/server -db ./data.db` — HTTP server on `:8080` with auto-rebuild on file change |
| `make wire` | regenerate `wire/wire_gen.go` |
| `make mock` | regenerate `domain/mocks/*` |
| `make all` | full from-scratch verification: install + regenerate + lint + test |

## REST API

The HTTP server (`cmd/server`) exposes:

| Method | Path | Purpose |
|---|---|---|
| `GET`  | `/health` | liveness probe, returns `{"status":"ok"}` |
| `POST` | `/orders/validate` | read-only validation, returns the `Result` (see schema below) |
| `POST` | `/orders/process` | validate **and** execute: debits/credits balance, inserts audit row, increments daily ledger — all atomic in one tx. Requires `Idempotency-Key` header. Only available in GORM/SQLite mode (`-db <path>`). |

### Request body — `Order`

```json
{
  "customer_id": "C001",
  "order_type": "buy",
  "quantity": "0.5",
  "quoted_price": "42210"
}
```

- `customer_id` (string, required) — must exist in `accounts` table when running with GORM/SQLite
- `order_type` (string, required) — `"buy"` or `"sell"`
- `quantity` (decimal as string, required) — positive multiple of 0.5 baht-weight, ≤ 1000
- `quoted_price` (decimal as string, required) — positive THB / baht-weight, ≤ 10,000,000

Unknown fields are rejected with `400 Bad Request` (`DisallowUnknownFields`).

### Response body — `Result`

```json
{
  "valid": false,
  "errors": [
    { "code": "DAILY_LIMIT_EXCEEDED", "field": "quantity",
      "message": "order quantity 1.5 exceeds remaining daily allowance 1 baht-weight" }
  ],
  "expected_buy_price": "42210",
  "spread": "210",
  "daily_remaining": "1"
}
```

- `valid` — `true` only when every rule passed.
- `errors` — every failure collected in one pass (the validator deliberately does **not** short-circuit between rules in the same phase).
- `expected_buy_price` / `spread` — populated for buy orders.
- `daily_remaining` — populated when a `DailyLedger` is configured. On rejection it's the headroom *before* this order; on acceptance it's the allowance *after*.

## What the seed populates

`make seed` runs **Atlas** (`atlas schema apply --to file://schema.sql`) to create the `accounts` and `daily_totals` tables declaratively, then `cmd/seed` inserts sample rows:

| customer_id | balance (THB) |
|---|---|
| C001 | 1,000,000 |
| C002 | 500 (intentionally not enough for a 1-baht-weight buy at market) |
| C003 | 5,000,000 |

Plus one `daily_totals` row: `C001` has already traded 4 baht-weight today, leaving 1 baht-weight headroom until the 5 baht-weight daily limit kicks in.

## Hardening beyond the bare assessment requirements

- **Config validation.** Each module's `New(...)` validates its `Config` and rejects nil dependencies up front; misconfigured deployments fail at construction, not at first call.
- **Sanity ceilings.** `MaxQuantity`, `MaxPrice`, `MaxCustomerIDLength` cap inputs *before* any DB or market lookup.
- **Customer-ID scrubbing.** Empty IDs, leading/trailing whitespace, or control characters (NUL etc.) are rejected — blocks log-injection and downstream DB-shape surprises.
- **Stable error codes.** Every code is an exported constant (`balance.CodeInsufficientBalance`, `quote.CodeStaleOrOffPrice`, …) so callers branch on them without parsing English.
- **Fail closed on infrastructure errors.** Missing market price → `MARKET_UNAVAILABLE`. Ledger read failure → `LEDGER_LOOKUP_FAILED`. Order rejected, not silently passed.
- **Thread-safe in-memory adapters.** `balance.Memory`, `limit.Memory` use mutexes; the validator is stateless and safe to share. Covered by `-race` tests.
- **Transactional GORM ledger.** `repositories.Ledger.Record` runs under `db.Transaction` with `clause.Locking{Strength: "UPDATE"}` (SELECT FOR UPDATE on Postgres/MySQL; serialised transaction on SQLite). Prevents the lost-update race that two concurrent records of the same customer-day would otherwise produce.
- **Benchmarks.** `BenchmarkValidate_HappyBuy` and `BenchmarkValidate_RejectedDailyLimit` live in `domain/service/validator/bench_test.go`; run with `go test -bench=. -benchmem -run='^$' ./domain/service/validator`.
- **HTTP hardening.** `cmd/server` sets `ReadHeaderTimeout`, `Read/WriteTimeout`, `DisallowUnknownFields` on the JSON decoder, graceful shutdown on `SIGINT`/`SIGTERM`.
